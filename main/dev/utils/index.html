    Architecture of coola.utils¶

    This page describes the design of the coola.utils package for contributors: the invariants, the contracts between the parts, and the decisions behind them. The rules that users rely on are in the user guide; the API is in the reference.

    Constraints¶

    1. Simple and easy to maintain. coola.utils is 4,002 lines in 23 modules and two subpackages (imports 957, fallback 396), tested by 5,561 lines. It mixes the foundation of coola (imports, singletons, introspection) with standalone helpers (Bloom filter, LRU cache, git, dates) that no other package imports. The package removes the repetition (the same four functions were written eleven times) and deletes only what is risky or obsolete. The useful helpers are kept, with their tests.
    2. Major release. Breaking changes are fine and compatibility is not a design input: no alias, no deprecation period (a moved module is imported from its new path). The release notes and the migration page (docs/docs/migration/v1.1_to_v2.0.md) list the changes.
    3. The rules of the repository apply to the helpers too. Options are keyword-only, an argument check goes through coola.validation, a shared helper is public and tested, a lazily built process-wide object is a LazySingleton.
    4. A leaf of the layering. utils is below every other package. It may import the standard library and coola.validation, nothing else (the lint-imports contract "Utils must import validation only"). registry depends on utils, never the opposite. The formatting package sits above it (it may import utils and validation).
    5. Optional libraries stay lazy. Importing coola.utils or coola.utils.imports imports no optional library, and the availability helpers are the one mechanism the other packages use to ask whether a library is there.

    formatting is a core package next to utils: every function that turns a value into a string for a message, a repr or a report is there (before: they were spread over utils.format, utils.string, utils.secret and utils.text_diff, and display and registry imported the first). It may import utils (sort_by_keys) and validation, and no other package. display, registry and the feature packages import from it. The name is decision D1b: coola.format would shadow the builtin in from coola import format.

    The modules that no other package imports (array, batching, bloom_filter, date, env_vars, file_size, git, logging, lru, password, recursion, timing) stay public and documented in the same page as the core helpers (docs/docs/uguide/utils.md, refs/utils.md). They were moved to a coola.tools package (decision D1) and then back into coola.utils, so there is one place for the helpers and one import path per function.

    Moved elsewhere: coola/registry/default.py (make_default_registry_singleton, reset_default_registries, temporary_default_registries), coola/registry/plugins.py (load_registry_plugins, get_loaded_plugins, LoadedPlugin, the two environment variable names) and coola/nested/conversion.py (to_jsonable, which only nested calls and whose docstring sends the reader to nested). Deleted: get_fully_qualified_name (replaced by get_qualified_class_name), working_directory (contextlib.chdir) and deprecate_positional_options (no caller).

    imports: one definition of "available"¶

    The current design copies one 100-line module per library. The four functions are the same except for a string, and two of them are unused or harmful. The target keeps what the 66 files that import it use and nothing else.

    package.py (was universal.py) defines the mechanism once, with one message:

    class MissingPackageError(ModuleNotFoundError, RuntimeError): ...  # unchanged


def availability_cache(fn: F) -> F: ...  # unchanged
def clear_availability_caches() -> None: ...  # unchanged
def package_available(name: str) -> bool: ...  # installed, not imported (find_spec)
def module_available(name: str) -> bool: ...  # importable, imported, cached


def check_package(package: str, *, install: str | None = None) -> None:
    """Raise ``MissingPackageError`` unless ``module_available(package)``."""


def raise_package_missing_error(package: str, *, install: str | None = None) -> Never:
    """The one message: ``'x' package is required ...`` with ``pip install`` and ``uv pip install``.
    ``install`` is the pip name when it differs from the import name (the default)."""

    optional.py is the only place that names a library. For each library, two functions with the same two lines:

    @availability_cache
def is_numpy_available() -> bool:
    r"""Indicate if ``numpy`` is installed and can be imported. ..."""
    return module_available("numpy")


def check_numpy() -> None:
    r"""Check that ``numpy`` is available. ..."""
    check_package("numpy")

    so that check_numpy() is by definition check_package("numpy"), and is_numpy_available keeps its name for the 66 files that import it and for the if TYPE_CHECKING or is_numpy_available(): idiom, which needs a statically known name. The torch and NumPy pair keeps its compatibility check (torch.tensor([1.0]).numpy()), imported inside the function.

    Deleted from the public surface: the eleven decorators x_available and torch_numpy_available (no caller, silent None), decorator_package_available, the eleven raise_x_missing_error (the fallback modules call raise_package_missing_error through make_fake_class("numpy")), LazyModule, lazy_import and import_object (replaced by pkgutil.resolve_name, ). The check_package signature loses its positional command: the install keyword is the pip name, and the message is the same as for every other package.

    lazy.py keeps lazy_exports (eight packages) and is_module_imported (factory).

    Adding a library (docs/docs/dev/add_backend.md) is two functions in optional.py, their names in imports/__init__.py, one fake module in fallback/<pkg>.py and one row in testing/marks.py, plus pyproject.toml: about 25 added lines instead of a 100-line module copied from pandas.py.

    LazySingleton and the default registries¶

    utils/singleton.py keeps the primitive and makes the two private test hooks public, so that the code that moves out does not need the privates:

    class LazySingleton(Generic[T]):
    def get(self) -> T: ...  # unchanged
    def is_built(self) -> bool: ...  # unchanged
    def reset(self) -> None:  # raises RuntimeError from the factory's own thread
        ...

    def set(self, value: T) -> None:  # new: replaces the cached value, under the lock
        ...

    coola/registry/default.py receives make_default_registry_singleton(registry_cls, register_defaults, *, plugin_group=None), reset_default_registries() and temporary_default_registries(); the last one is written with is_built, get, set and reset: on entry, set(get().copy()) for each registry that is built; on exit, set(original) for those registries and reset() for the ones that were built inside the context. The module already knows what a registry is (it calls copy), so its place is coola.registry. coola/registry/plugins.py receives the entry-point loader, LoadedPlugin, get_loaded_plugins and the two environment variable names (COOLA_STRICT_PLUGINS, COOLA_DISABLE_PLUGINS) with their two-line _env_flag. Behaviour is unchanged. The six feature packages and coola.testing import from coola.registry instead of coola.utils.singleton; coola.random already depends on coola.registry (its registry is a Registry).

    LazySingleton.reset () -> None raises RuntimeError when called by the thread that builds the value
    compare_version (package, op, version) none

    Rule for a new helper¶

    A helper used by two or more packages of coola goes to coola.utils (CLAUDE.md), public and tested. A general-purpose helper that coola does not use also goes to coola.utils. Both are generic, and a helper that is a step of one feature lives in that feature. A function that turns a value into text goes to coola.formatting. No test enforces the role of utils (decision D4): the review and the lint-imports contracts do.

    Decisions for the maintainers¶

    Status: all decisions are taken. The recommendation was followed everywhere except two: D2 (only working_directory is removed; password and recursion are kept) and D4 (no census test for now). D1 was reversed afterwards (see below).

    D1. Name and shape of the new sub-package. Recommended: coola.tools, one module per theme, the modules moved as they are. It keeps the useful helpers, keeps their tests, and lets utils be the foundation. Alternatives for the name: coola.helpers, coola.extras. Alternative for the shape: group the modules by theme (structures: Bloom filter, LRU, batching; text: string, secret, text_diff; system: git, env_vars, file_size, timing), which is a better public API but a rewrite of the paths and of the tests, not a rename. Not recommended now; a later step can do it once the move is merged.

    Decided: follow the recommendation. coola.tools was created (#2569), then moved back into coola.utils (#2579): two packages of helpers split the documentation and the import paths for no benefit, so the standalone helpers are modules of coola.utils again, in the same user guide page.

    D1b. A coola.formatting sub-package? Recommended: yes, named coola.formatting. The functions that format are in four modules of utils and the formatting is the base of display (InlineDisplayMixin builds its repr with str_mapping and repr_indent) and of the error messages of registry. One package makes them discoverable and lets utils stay the foundation. Alternatives: coola.format (shorter, shadows the builtin when imported as from coola import format); coola.text (the byte and time functions are not text); fold it into coola.display (display is the user-facing mixin; registry would then depend on display, which the layering guide does not allow today). The sequence and mapping functions stay in one module (structure) because they share str_indent.

    Decided: yes, coola.formatting.

    D2. Delete password, recursion and working_directory? Recommended: yes. They were the only three items proposed for removal. password handles credentials (the risk of a bug is a security issue, the benefit to coola is nil), working_directory is contextlib.chdir, and recursion explains an error that no function raises since the explicit stacks. Alternative: keep password; it is tested (233 lines), and the risk is small if nobody calls it, but it is code that a comparison library gets asked about in a security review.

    Decided: remove working_directory only; keep password and recursion for now and re-examine them later.

    D3. Move the default registries and the plugin loader to coola.registry? Recommended: yes. It is registry code (it copies registries, it loads entry points into them), and it is what LazySingleton should not know. The cost is a changed import in seven packages, which lint-imports checks. Alternative: split singleton.py in singleton.py, default_registry.py and plugins.py inside utils; cheaper, but utils would keep a concept it should not know.

    Decided: follow the recommendation.

    D3b. One optional.py or one module per library? Recommended: one module. The 11 modules differ by a string; a single module makes the repetition visible and a parametrized test covers all of them. The cost is 21 patches in tests and the add_backend.md recipe. Alternative: keep one module per library with two functions each (about 35 lines): the same patch paths, the same recipe, 400 lines instead of 330 and 11 test files instead of one.

    Decided: follow the recommendation.

    D4. Enforce the role of utils with a test? Recommended: yes, as an integration test. A rule that rests on discipline is the rule that produced : 16 modules were added to utils with their tests, each for a reason that was true on the day. The test is 30 lines and fails when a module of utils is imported by no other package (it then moves to a package that uses it, or is deleted). It checks modules, not names, so nothing useful is deleted. Alternative: only the sentence in the guide and CLAUDE.md.

    Decided: not now. The ast census test is not added; the role of utils is kept by review and by the lint-imports contracts.

    D5. Change the hash of a huge negative integer? Recommended: yes. 0x-1000… is not a representation of the number, and a hash is only stable inside a version of coola (hashing states that the hashes may change between major versions). Only a negative integer with more than 4,300 digits is affected. Alternative: keep the bug and document it; not recommended because the fix is the only way to keep int_repr equal to hex(value) for the negative case.

    Decided: follow the recommendation.

    D6. Replace import_object by pkgutil.resolve_name? Recommended: yes. Same format ("pkg.mod:name"), same errors, and no second function named like the one of coola.factory. The only difference is "pkg.mod:", which returns the module instead of raising; nobody passes it.

    Decided: follow the recommendation.

    D7. Make _reset_after_fork public? Recommended: no. It is a hook for the fork handler, not part of the API of a registry or of LazySingleton. The protocol (ForkAware) says so. A callback passed to track_fork(obj, callback) would need a WeakMethod for the same effect, with more code.

    Decided: follow the recommendation.

    Not covered¶

    • The fallback idiom (if TYPE_CHECKING or is_numpy_available(): import numpy as np else: from coola.utils.fallback.numpy import numpy as np) appears in 46 files. It makes isinstance(x, np.ndarray) false when NumPy is missing. A different mechanism (a lazy proxy, a typed stub) is a separate design; this one only makes the fakes cheaper to write.
    • coola.testing (the x_available marks, the fixtures) is only a caller here. The marks keep their one-row-per-dependency table.
    • coola.display is only a caller here. Removing timing removes its dependency on utils for good, but display keeps importing format, mapping and imports.
    • Windows: os.register_at_fork is absent there, so track_fork is a no-op (documented); the fork behaviour was not run on Windows.
    • Performance: no helper of utils is on a hot path except track_fork (called once per object) and is_<pkg>_available (cached); no benchmark gate is needed for this item.
    • Import time of importlib.metadata (7.5 ms) loaded by singleton.py for the plugin loader: it leaves utils with the loader in and is then paid by coola.registry, not by coola.utils.
